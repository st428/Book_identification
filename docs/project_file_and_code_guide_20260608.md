# final 项目文件与代码说明

本文档用于说明 `D:\个人\university\2026spring\lib\final` 最终版项目的文件组成、运行流程和主要 Python 代码功能。最终版定位为“官方 OCR 稳定版”：不再接入自训练识别模型，重点保证 Web/手机端可用、检测框稳定、缓存清晰、结果展示明确。

## 一、项目总体思路

本项目面向图书馆横排书架巡检场景。用户上传一张或多张书架图片后，系统先定位书脊底部的红色标签区域，再在红色标签附近裁切索书号 crop，调用官方 PaddleOCR 识别书号，最后根据索书号排序规则判断当前排列是否正常。

项目不做数据库馆藏比对，也不自动判断“缺失书籍”。红色表示系统认为该书号位置可能不符合当前书架顺序，黄色表示 OCR、crop 或补框结果需要人工复核，绿色表示当前识别和排序判断未发现明显问题。

## 四、mobile_web 前端文件

`mobile_web/index.html` 是单页 Web 界面。主要包含图片选择、多图上传、普通/精细模式选择、识别按钮、OCR 状态显示、结果列表、标注图展示和 crop 诊断链接。

`mobile_web/style.css` 控制页面样式。最终版的设计目标是手机端可读、电脑端可扫视，颜色与后端状态一致：绿色表示通过，黄色表示复核，红色表示疑似错架。

## 五、shelf_inspector_fast.py 代码结构

### 1. 数据对象

文件开头定义 `OcrLine`、`Detection`、`ImageRunResult` 等数据类。它们把检测框、OCR 文本、置信度、状态、原因、推荐位置、crop 路径等信息统一保存起来，方便后续导出 JSON、CSV、HTML 和 Web 返回。

### 2. 图片读取与方向处理

`read_image`、`write_image`、`rotate_image`、`resize_for_speed` 等函数负责读取图片、写出图片、旋转图片和缩放图片。项目中的书号大多在书脊底部，拍摄方向不稳定时需要先尝试方向判断，再进入后续检测。

### 3. 红色标签检测

`build_red_mask` 和相关辅助函数通过 HSV 颜色空间提取书脊底部红色标签区域。这样做的原因是索书号通常贴在红色标签附近，先找红色标签可以减少整图 OCR 的范围，提高速度和稳定性。

### 4. OCR 加载与结果解析

`load_paddle_ocr` 负责加载 PaddleOCR。最终版 Web 端固定使用官方 OCR，不读取自训练模型环境变量。`flatten_ocr_result` 用来把 PaddleOCR 不同版本可能返回的嵌套结构整理成统一的文本行。

### 5. OCR 文本规范化

`normalize_ocr_text`、`parse_call_number` 等函数把 OCR 原文转换成更接近真实索书号的格式。例如把容易混淆的 `O` 和 `0` 修正到合理位置，过滤明显不完整文本，并检查 `/` 后首字符是否为字母。

### 6. 排序判断

`call_number_order_key` 把索书号转换成可比较的排序键。`apply_sort_status` 根据当前顺序和排序后顺序决定绿色、黄色、红色状态。不完整书号或低置信结果不直接参与红色错架判断，而是标为黄色等待人工复核。

### 7. 后处理修正规则

中段的修正规则处理常见错误：相邻书号末位数字串号、末位 `1` 被分给右侧 crop、书号末尾出现不合理字符、`II` 被误认为真实分类号开头、`ED669.3/...` 这类左侧粘入多余字母等。这些规则不替代 OCR，只修正有明确规律且风险较低的问题。

### 8. 横排书架 crop 生成

`make_code_strip_box`、`build_horizontal_detections`、`expand_horizontal_crop_y_bounds` 等函数根据红色标签和文字位置生成底部索书号 crop。普通模式更偏向速度，精细模式会保留更多边界和重试空间。

### 9. 精细模式 crop retry

`clamp_crop_box` 及后续 retry 函数会在 OCR 失败、crop 可疑或边界过紧时尝试扩大、平移或重新裁切。精细模式速度更慢，但对少量疑难图更适合人工复核。

### 10. 漏检补框

`densify_horizontal_detections` 会检查相邻检测框之间是否存在异常大空隙。如果疑似漏了一本书，会生成黄色补框。黄色补框不会直接参与红色错架判断，避免系统把推测结果当成确定错误。

### 11. 候选书号构造

`build_ocr_candidates` 会把 PaddleOCR 返回的多个文本片段组合成候选书号。例如一个 crop 中分类号和作者号被识别成两行时，需要合并后再判断是否符合索书号格式。

### 12. 结果导出

`annotate_image`、`write_report_csv`、`write_summary`、`write_crop_diagnostics_html` 负责导出标注图、CSV、JSON 和 crop 诊断页。Web 前端主要读取 `summary.json` 中的结构化信息，同时给用户提供诊断页链接。

### 13. 单图主流程

`inspect_image` 是单张图片的核心入口，基本流程是：读取图片、缩放、方向判断、红色标签检测、生成检测框、OCR、后处理、排序判断、姿态提示、写出结果文件。这个函数也是 Web 端和命令行共同使用的核心函数。

### 14. 批处理入口

`run_inspection` 和 `main` 负责命令行批处理。它们可以接收文件或文件夹路径，批量处理图片，并把每张图片的结果写到指定输出目录。

## 六、mobile_server.py 代码结构

### 1. 路径与模式配置

`WORKSPACE` 指向 final 根目录，`UPLOAD_DIR` 和 `RESULT_DIR` 分别保存上传文件和结果缓存。`WEB_CACHE_VERSION` 是 Web 缓存版本号，当前为 `web_official_ocr_stable_20260608_v5`。如果后续修改检测规则、crop 规则或结果格式，应更新这个版本号。

`WEB_MODES` 定义两种模式：普通模式使用 `max_side=1200` 且不开启 crop retry；精细模式使用 `max_side=1600` 且开启 crop retry。

### 2. OCR 常驻缓存

`ensure_ocr_loaded` 使用线程锁保证 PaddleOCR 只加载一次。多个请求同时到来时，后来的请求会等待已有加载过程完成，避免重复加载 OCR 导致速度更慢或内存占用过高。

### 3. 上传图片保存

`save_uploaded_image` 检查图片扩展名，读取上传内容，并用 SHA256 哈希生成文件名前缀。同一张图片重复上传时会复用已有文件，从而配合结果缓存减少重复计算。

### 4. 结果缓存命名

`output_variant_for_mode` 把 Web 缓存版本、OCR 策略和模式拼成缓存命名空间。这样普通模式和精细模式不会互相覆盖，旧版本缓存也不会误显示给用户。

### 5. 结果序列化

`serialize_result` 把 `ImageRunResult` 转成前端需要的 JSON，包括标注图 URL、诊断页 URL、绿色/黄色/红色数量、每个书号的状态、原因、置信度和调架建议。

### 6. Web 接口

`/api/status` 返回 OCR 加载状态、OCR 策略、缓存版本和可选模式。`/api/preload` 用于后台预加载 OCR。`/api/inspect` 接收多图上传并调用 `run_inspection`。`/results/<path>` 用于访问标注图、诊断页和结果文件。

### 7. 启动流程

`main` 会打印电脑端和手机端访问地址，然后在后台预加载 OCR，最后启动 Flask 服务。`启动Web端.exe` 本质上就是更方便地调用这个流程。

## 七、普通模式和精细模式

普通模式的目标是日常巡检速度。它缩放到较小尺寸，不开启 crop retry，适合大部分清晰、正对书架的图片。

精细模式用于少量 OCR 失败、crop 可疑或黄色结果较多的图片。它保留更大输入尺寸并开启重试，因此速度明显慢于普通模式，不建议作为全部图片的默认模式。

## 八、项目结果如何解释

绿色：识别文本格式正常，排序判断没有发现明显异常。

黄色：结果需要人工复核，常见原因包括 OCR 置信度低、crop 不完整、疑似漏检补框、书号不完整、图片姿态不佳等。

红色：系统认为该书号位置可能不符合排序规则，并会尝试给出调架建议。红色结果仍然需要先确认 OCR 文本和 crop 是否正确，再决定是否真的移动书籍。

## 九、最终版的边界

最终版重点是稳定可用，不追求完全自动化。对于远距离、严重倾斜、遮挡、污渍、手写体、极薄书脊或 crop 过窄的图片，系统可能仍需人工复核。项目当前没有接入馆藏数据库，因此不会判断某本书是否缺失，也不会验证某个索书号是否属于该书架。
