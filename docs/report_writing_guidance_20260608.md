# Python 课程项目报告写作指导

本文档根据课程报告模板和本项目真实实现整理，只用于指导报告组织，不是可直接提交的完整报告。

## 一、适合采用的报告结构

建议按照老师模板写，不要另起论文式结构：

1. 项目简介
2. 项目开发中的难点问题
3. 采用的关键技术或主要方法
4. 实现效果及分析
5. 总结

模板首页还需要补充姓名、学号、专业、年级和 GitHub 托管网址。正文至少 3000 字、8 页左右，截图和表格要配标题。

## 二、每一部分重点写什么

### 1. 项目简介

重点写清楚项目名称、应用场景和最终功能。可以说明项目是“图书馆书架智能巡检与索书号识别系统”，主要解决手机拍摄书架后自动识别索书号、标记疑似错架、辅助人工巡检的问题。

不要写成“完全替代人工巡检”。更真实的表达是：系统用于提高初步检查效率，黄色和红色结果仍需人工确认。

建议写到的功能：

- Web/手机端上传图片；
- 支持多图上传；
- 支持普通模式和精细模式；
- 自动检测书脊底部索书号区域；
- 调用官方 PaddleOCR 识别；
- 输出绿色、黄色、红色结果；
- 保存标注图、crop 诊断页、CSV、JSON；
- 使用缓存避免重复识别同一张图。

### 2. 项目开发中的难点问题

这一部分最适合体现真实开发过程。建议重点写以下几类：

- 书架图片拍摄角度不固定，倾斜和远距离会影响检测；
- 书脊宽度差异大，薄书容易漏检；
- 红色标签、污渍、遮挡会影响 OCR；
- crop 裁切太窄会导致末位数字漏识别，太宽又可能吃到相邻书号；
- 训练自定义 OCR 模型后效果没有稳定超过官方 OCR；
- Web 端需要处理多图上传、缓存版本和结果展示。

不要只写“遇到很多 bug，经过努力解决了”。要结合具体例子，例如薄书、末位 1 串号、姿态较差图片直接提示重拍等。

### 3. 采用的关键技术或主要方法

这一部分可以分模块写：

- Python + Flask：实现 Web/手机端服务；
- OpenCV：读取图片、颜色阈值、红色标签区域检测、绘制标注框；
- PaddleOCR：识别 crop 中的索书号文本；
- dataclass：保存 OCR 行、检测框和整图运行结果；
- JSON/CSV/HTML：保存识别结果、报告和 crop 诊断页；
- 文件哈希和缓存版本：避免同图重复处理，避免旧缓存误用；
- 正则表达式和后处理规则：规范化索书号格式，修正常见 OCR 错误；
- 排序键：将索书号转成可比较结构，用于判断书架顺序。

注意不要写数据库、深度学习模型部署、馆藏比对、自动缺失书判断，因为最终版没有做这些。

### 4. 实现效果及分析

这里建议放截图和表格。可以使用：

- Web 首页截图；
- 上传后结果列表截图；
- 标注图截图；
- crop 诊断页截图；
- `docs/final_demo_test_20260608.md` 中的普通/精细模式测试表；
- 红色错架示例截图；
- 姿态较差提示重拍的例子。

分析时要写优缺点：

- 普通模式速度较快，适合日常使用；
- 精细模式更慢，但适合 OCR 失败或 crop 可疑图片；
- 官方 OCR 比自训练模型更稳定；
- 对严重倾斜、遮挡、手写体、污渍和过薄书仍然有限制。

### 5. 总结

总结可以写自己完成了从命令行脚本到 Web 端的整理，最终选择官方 OCR 稳定版，并通过缓存、多图上传、crop 诊断和颜色结果展示提高实用性。

不要写“系统已经完全准确识别所有书籍”。可以写“在课程项目范围内实现了可运行、可展示、可复核的版本”。

- 项目功能：配 Web 首页和结果页截图；
- 关键技术：引用 `shelf_inspector_fast.py` 和 `mobile_server.py` 的主要函数；
- 数据保存：截图或说明 `stage5_mobile_results/uploads`、`results`、`final_demo_results`；
- 测试结果：引用 `docs/final_demo_test_20260608.md` 表格；

报告中可以直接写“代码中通过 `Detection` 保存单个检测框信息，通过 `ImageRunResult` 保存整张图片结果”，这种表述比大段贴代码更合适。

## 四、不能乱写或不能夸大的内容

- 不要写系统接入了图书馆馆藏数据库；
- 不要写可以自动判断缺失书籍；
- 不要写自训练 OCR 模型已经优于官方 OCR；
- 不要写识别准确率达到 100%；
- 不要写使用了复杂的深度学习检测模型，如果代码主要依靠 OpenCV 颜色和规则检测；
- 不要把黄色补框写成确定漏检结果，它只是疑似框；
- 不要把红色结果写成绝对错架，实际仍需人工确认 OCR 和 crop。

## 五、可以体现自己完成过程的细节

建议写一些具体开发取舍：

- 一开始尝试训练识别模型，但整图对比发现速度和识别稳定性不如官方 OCR，所以最终版固定官方 OCR；
- 发现主要瓶颈不是 OCR 模型本身，而是检测框和 crop 质量；
- 为了避免误判，系统把不完整书号和补框标黄，不直接参与红色错架判断；
- 普通模式和精细模式分开缓存，避免不同模式结果混在一起；
- 对姿态很差的图片直接提示重拍，避免浪费 OCR 时间并输出大量错误结果；
- crop 诊断页用于检查书号有没有裁全，便于人工复核和后续调试。

## 六、老师可能会问的问题

1. 为什么不用数据库比对？

可以回答：课程项目重点放在图片识别和书架顺序辅助判断，数据库比对需要真实馆藏数据和书架范围信息，当前版本没有可靠数据来源，因此没有实现。

2. 为什么最终不用自己训练的 OCR 模型？

可以回答：做过训练和整图对比，但自训练模型在部分类别上更慢、漏识别更多，最终为了稳定性选择官方 OCR。

3. 黄色、红色分别是什么意思？

可以回答：黄色是需要人工复核，可能是 OCR 低置信、crop 可疑或疑似补框；红色是排序上疑似错架，但仍需先确认 OCR 文本正确。

4. 普通模式和精细模式有什么区别？

可以回答：普通模式缩放更小、不重试 crop，速度快；精细模式保留更大图像并开启 crop retry，适合少量问题图。

5. 缓存有什么用？

可以回答：同一张图片重复上传或同一模式重复识别时，可以复用结果，减少等待时间；缓存版本变化后会生成新结果，避免旧逻辑影响展示。

6. 系统最容易失败的情况是什么？

可以回答：严重倾斜、远距离、污渍遮挡、手写体、红色遮挡书号、极薄书脊和 crop 边界不完整。

## 八、已有文本修改建议

如果你已经写了报告初稿，建议重点检查：

- 是否有“万能模板句”，例如“本项目具有重要意义、系统功能完善、运行效果良好”，这些句子要改成具体功能和截图说明；
- 是否把未实现功能写进去了；
- 是否有大段代码粘贴，报告更适合放关键函数说明和流程图；
- 是否只写成功结果，没有写局限性；
- 是否没有解释为什么最终选择官方 OCR；
- 是否没有写数据和结果文件保存在哪里。
