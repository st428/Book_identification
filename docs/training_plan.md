# 自训练 OCR 模型实验说明与工程复盘

本文档记录本项目中自训练索书号识别模型的实验过程、实际结果、未接入最终 Web 版本的原因，以及从工程角度得到的反思。这里的“自训练模型”主要指在 PP-OCRv5 mobile 文字识别模型基础上的领域微调，而不是从零开始训练完整 OCR 系统。

最终结论是：当前最终版 Web 端固定使用官方 PaddleOCR，不部署自训练模型。自训练模型相关工作作为实验过程和后续改进储备保留。

## 一、训练目标

项目早期希望通过自训练模型提升图书索书号的识别稳定性，尤其是以下场景：

- 书脊底部索书号较小、字符较密；
- `D669.3/HW2`、`D669.3/YMZ1` 等末位数字容易漏识别；
- `Z/T/7`、`O/0`、`H/N` 等字符容易混淆；
- 薄书或相邻书号距离过近时，OCR 结果容易串入相邻书号；
- 部分非 `D669.3` 类号、带短横线或 `2026` 的书号结构识别不稳定。

因此，自训练实验的初始设想是：收集人工校验后的 crop 图片和标签，训练一个更贴近图书馆索书号格式的识别模型，再替换 Web 端默认 OCR。

## 二、数据整理过程

训练数据主要来自 Web 端和命令行批处理生成的 crop。处理流程大致如下：

1. 从原始书架图片中检测红色标签和底部书号区域，导出每个检测框对应的 crop。
2. 生成人工复核表，人工检查 OCR 文本、crop 是否完整、是否只包含一本书的索书号。
3. 将人工确认可用的样本整理为识别训练数据。
4. 按训练集和验证集划分，保留独立验证结果用于评估。
5. 训练结束后导出 inference 模型，再放回整图流水线中做真实场景对比。

后期训练中明确排除了以下样本：

- 空白框、纯背景框或只截到书架缝隙的框；
- 被红色标签严重遮挡、无法看清完整书号的 crop；
- 只截到半个书号或混入相邻书号的 crop；
- OCR 结果和图片实际内容不一致且无法人工确认的样本；
- 由漏检补框推测出来、但没有可靠人工确认的样本。

这个筛选原则是为了减少“错误标签”进入训练集。对于文字识别模型来说，错误标签的危害通常比样本数量不足更大。

## 四、整图对比结果

为了判断模型是否具有实际使用价值，项目进行了整图级别对比。对比输出位于：

```text
D:\upload_ascii\stage5_mobile_results\model_compare\guarded_ep2_20260603\index.html
```

对比对象包括：

- `web_current`
- `rotated_best_accuracy`
- `rotated_iter_epoch_6`
- `guarded_best_accuracy`

实际对比结果显示，`guarded_best_accuracy` 不适合作为 Web 默认模型：

- 处理速度慢于当前官方 OCR；
- 整图中成功识别出的书号数量更少；
- 红色结果更多，但其中一部分是 OCR 退化导致的误判；
- 对部分原本官方 OCR 能识别的书号出现截断或字符替换。

典型退化包括：

| 正确或较优结果 | 自训练模型结果 | 问题类型 |
| --- | --- | --- |
| `D669.3/LZF` | `D669.3/ZF` | 漏掉首字母 |
| `D669.3/QLY` | `D669.3/QL` | 末位字母缺失 |
| 完整书号 | `CC2`、`A` | 输出过短或结构异常 |
| 完整书号 | `D669.3/H` | 作者号截断 |

这些问题会直接影响排序判断。索书号任务中，一个字符错误就可能改变排序位置，因此“看起来相似”的 OCR 输出在工程上仍可能不可用。

## 五、未采用自训练模型的原因

最终版没有部署自训练模型，主要原因不是训练过程失败，而是它没有在实际 Web 场景中稳定超过官方 OCR。

### 1. 主要瓶颈不在识别模型本身

项目后期复核发现，许多错误来自检测框和 crop 质量：

- 书号没有完整裁进 crop；
- 相邻书号过近，左框或右框吃到对方字符；
- 薄书没有被稳定框出；
- 红色标签遮挡了部分底部字符；
- 倾斜和远距离拍摄导致书号区域过小。

如果 crop 本身不完整，即使更换识别模型也很难得到正确书号。因此，继续增加训练轮数不能从根本上解决检测和裁切问题。

### 2. 验证集指标不等于整图效果

验证集中的 crop 往往已经经过人工筛选，质量高于真实 Web 上传中的所有 crop。模型在验证集上取得较好指标，并不代表它在整图流水线中会更好。

整图场景还包含检测误差、旋转误差、边界截断、补框、低清晰度图片和后处理规则等因素。任何一个环节的小错误都可能被排序判断放大。

### 3. 样本覆盖仍然不足

虽然 3052 个样本对课程项目来说已经不少，但对 OCR 微调仍然偏小，尤其是索书号结构具有明显长尾：

- 分类号不只包含 `D669.3`；
- 作者号中存在不同长度的字母组合；
- 末位数字、短横线、冒号和年份结构分布不均；
- 拍摄角度、书脊颜色、印刷字体和污渍遮挡差异较大。

模型容易学习到训练集中高频模式，但在低频结构上退化。

### 4. 错误标签和边界样本会降低模型可靠性

训练数据来自自动检测框导出的 crop，天然依赖检测框质量。即使经过人工复核，也仍可能存在边缘样本：

- crop 看似包含完整书号，但末位数字很模糊；
- 一张 crop 中包含两个相邻书号的一部分；
- 人工标签根据上下文推断，但图片本身并不清晰；
- 红色遮挡下的字符无法直接从图像确认。

这些样本如果进入训练集，会让模型学习到不稳定映射。

### 5. 部署成本和回退风险较高

Web 端需要稳定、可解释、可复现的结果。接入自训练模型会带来额外问题：

- 推理速度变慢，影响手机端使用体验；
- 模型路径、缓存版本和官方 OCR 结果容易混用；
- 用户看到的红色错架可能来自模型误识别，而不是真实错架；
- 后续调试时更难判断问题来自 OCR、crop 还是排序规则。

因此，从工程角度看，在没有明确收益前，不应把自训练模型作为默认模型。

## 六、工程复盘

本项目的自训练实验说明，OCR 项目不能只把重点放在“训练模型”本身。对于书架巡检这种实际应用，完整链路至少包括：

1. 原图拍摄质量控制；
2. 红色标签和书号区域检测；
3. crop 边界是否完整；
4. OCR 模型识别；
5. 书号格式规范化；
6. 相邻书号后处理；
7. 排序判断；
8. Web 端缓存和结果展示。

在这条链路中，识别模型只是其中一环。当前阶段，影响最终结果的主要因素是检测框和 crop，而不是官方 OCR 本身的能力上限。

比较合理的工程顺序应当是：

1. 先保证 crop 尽量完整、只包含一本书；
2. 再建立可靠的人工复核数据集；
3. 然后小步训练识别模型；
4. 每次训练后立即做整图对比；
5. 只有当整图指标、速度和误判率都优于官方 OCR 时，才考虑部署。

本项目最终选择官方 OCR 稳定版，是一种工程取舍：优先保证系统可运行、结果可解释、用户体验稳定，而不是为了使用自训练模型而部署一个不稳定版本。

## 七、后续自训练模型的可能用途

虽然当前自训练模型没有接入最终 Web 版，但相关工作仍然有价值。后续如果继续扩展项目，自训练模型可以用于以下方向：

### 1. 作为精细模式的备选识别器

自训练模型不适合作为默认 OCR，但可以在精细模式中作为第二识别器，仅用于少量官方 OCR 失败且 crop 质量较高的样本。这样可以控制速度成本和误判风险。

### 2. 用于疑难样本分析

训练过程中的错误样本可以反过来帮助发现 crop 问题。例如模型频繁漏末位数字，可能说明裁切边界过紧；模型频繁混淆相邻字符，可能说明 crop 中混入了旁边书号。

### 3. 建立领域测试集

人工校验数据可以整理成固定测试集，用于比较不同检测规则、OCR 模型和后处理策略。即使不继续训练，数据本身也能作为项目质量评估依据。

### 4. 做轻量级后处理或候选重排

未来可以不直接替换 OCR 模型，而是把自训练结果作为候选之一，与官方 OCR 结果共同比较。系统可根据索书号格式、相邻顺序和置信度选择更合理的候选。

### 5. 支持更规范的数据闭环

如果后续继续训练，应建立更严格的数据闭环：

- 只使用完整、清晰、单书号 crop；
- 独立保留未参与训练的整图测试集；
- 按分类号、作者号长度、末位数字、拍摄角度分层统计；
- 每次只训练少量轮数；
- 训练后立即进行整图 Web 对比；
- 缓存版本必须包含 OCR 模型标识，避免新旧模型结果混淆。

## 八、最终结论

自训练模型实验完成了从数据导出、人工复核、训练、导出到整图对比的完整流程，但当前模型没有表现出相对官方 OCR 的稳定工程收益。

因此，最终 Web 版本采用官方 PaddleOCR，并把优化重点放在检测框稳定性、crop 完整性、漏检补框、黄色复核、缓存管理和结果展示上。自训练模型作为实验成果保留，后续只有在数据质量、测试集覆盖和整图对比结果都达到要求后，才适合重新考虑部署。
